# Wire services in `buildApp()` and let Fastify manage the pool

`buildApp()` is the composition root for Maria API. It stays synchronous and registers the database plugin first. During boot, Fastify runs the `/api` plugin's options callback after the database plugin exposes Kysely as `app.db`. The callback constructs the repositories and services in one place. The wiring relies only on documented Fastify behaviour, so the `/api` prefix sits on a wrapper plugin with object options rather than on the options callback, which Fastify documents only as returning the plugin's options. Each HTTP plugin receives its services through options, so route tests can supply fakes without starting PostgreSQL. [Issue #17](https://github.com/luis-neira/maria-api/issues/17) · [Issue #20](https://github.com/luis-neira/maria-api/issues/20) · [Fastify plugin options](https://fastify.dev/docs/latest/Reference/Plugins/#plugin-options) · [Route prefixing](https://fastify.dev/docs/latest/Reference/Plugins/#route-prefixing-option)

The database plugin opens and checks the PostgreSQL pool during boot and ends it in `onClose`, after Fastify drains in-flight HTTP requests. Production and integration tests share `buildApp()` and `app.close()`. Production boots through `listen()`, and integration tests can boot through `inject()` or use `ready()` to observe a boot failure. Overlapping `app.close()` calls share Fastify's cleanup. The executable keeps `close-with-grace`, including forced exit on a second signal or after the default 10-second timeout. [Fastify shutdown lifecycle](https://fastify.dev/docs/latest/Reference/Server/#shutdown-lifecycle)

The database plugin ends the pool if boot fails before it registers `onClose`. If `listen()` fails, the executable awaits `app.close()` before exiting unsuccessfully. Both paths preserve the original startup error if cleanup also fails. Regression tests will cover a failed bind with acquired database connections and an in-flight HTTP request that queries PostgreSQL during shutdown.
